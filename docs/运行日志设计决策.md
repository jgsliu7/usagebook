# 运行日志设计决策(ADR)

本文件记录 `usagebook-core::logging` / `usagebook-cli::logging_setup` 的关键设计裁决与理由,
供外部贡献者理解"为什么这样写"。实现细节以代码注释为准;行为契约以 README「运行日志」章节为准。

## D1|为什么自研写入器,不用 tracing-appender?

`tracing-appender` 的滚动只有时间维度(minutely/hourly/daily/weekly),没有大小轮转——
纯日期滚动挡不住单日日志风暴写满磁盘。它的 `non_blocking` 模式还有缓冲丢失问题:缓冲中
的日志在进程崩溃时丢弃,与"崩溃前日志必然落盘"的目标冲突。因此自研同步写入器(约 300 行核心),
代价是需要自己处理并发与失败路径——见 D4/D5。

## D2|日期 + 大小双重滚动,"轮转永不停止"

- 日期按**本地零点**(缓存"下一个本地零点的 epoch 时刻",与文件名日期同源;不用 UTC epoch-day,
  否则 UTC+14/DST 切换日与文件名系统性错位);
- 大小按**内存字节计数**(启动续开时 stat 一次校准),单文件 20MiB 内置常量;
- 分片号 `NNN` 取"当日已存在最大号+1",999 后自然进位 4 位——**任何路径下轮转不停止**:
  早先版本曾有"999 封顶后停止轮转+清理豁免活动文件"的组合,磁盘可被写满(评审中发现后移除);
- rename 瞬态失败(Windows 句柄占用等):继续写当前文件,30s 后重试——限频只作用于告警与
  失败重试,**成功轮转立即解除限频**;系统时钟回拨(now < last)视为窗口已过,否则回拨期间
  上限失效。

## D3|清理三规则与两类豁免

- 规则 A(保天数,默认 14 天)→ 规则 B(封总量,默认 200MiB,全序删除:先最老历史组整组、
  再当日分片从小号、最大号保底)→ 规则 C(围栏:只删 `usagebook.YYYYMMDD[.NNN].log` 与
  panic 两文件,其余一律不碰;只统计/删除 regular file,不跟随符号链接);
- 豁免 1:**当前活动主文件永不删**(删了它,Unix 下句柄继续写已 unlink 的 inode,日志静默消失);
- 豁免 2:**昨日的无分片主文件**——另一实例最后一次写在零点前时,其活动句柄正是昨日主文件
  (下一次写入即触发跨日轮转),外部清理者删它会制造一个刷新周期的静默丢失;更早的组不可能是
  活动句柄(写入前必先跨日轮转)。代价 ≤ 单文件 20MiB。

## D4|写路径纪律:旁路与锁外

写入路径内部(轮转失败/写失败/清理失败)的诊断**不得走 tracing**——那会重入写入器自身的锁:
溢出分支"记告警→计数仍超限→再告警"无限递归;持锁状态下同线程重入非重入锁则死锁,
`catch_unwind` 救不回卡在锁上的线程。因此:内部诊断一律 `eprintln!` 直写 stderr(容错写,
30s 限频);清理永远在锁外执行。

## D5|降级哲学(与 store 同构)

本产品的降级惯例是"打开失败→本进程降级直读,不退出"。日志层同构:目录不可写/锁被持有/
日志文件被预置为非常规文件(含符号链接,fifo 还会挂起写入)→ 文件层整体禁用 + console 提示,
看板照常服务。写失败:撕裂行在下一次写入前补 `\n` 修复;连续 3 次失败→文件层停写
(console 不受影响)——磁盘写满时"停写文件日志"优于"阻塞业务线程"。

## D6|目录锁:简版,一个反直觉裁决

双实例(不同端口)写同一日志目录会造成静默证据污染(A 轮转后 B 的 fd 跟随旧 inode)。
锁 = `O_EXCL` 创建 `.lock`(内容 pid):Unix 用 `kill(pid,0)` 判活——**EPERM 视为存活**
(那是"进程存在但属他户",共享目录场景;误回收比误占用危害大);ESRCH 判陈旧回收;
不可解析的锁与 Windows(无零依赖 pid 查活)以 mtime 年龄兜底(>1h 回收,"未来 mtime"
同样回收——否则时钟回拨会让死锁永不自愈)。取锁时序:**先绑端口后取锁**(端口失败保持
纯 exit 语义,双实例冒烟契约不回归)。残余风险(毫秒级 TOCTOU 窗口、NFS 跨机)README 声明。

## D7|panic 通道:独立、预建、双路脱敏

- 用 `set_hook` **替换**默认 hook(`std::panic::update_hook` 是不稳定 API,rustc 1.99 实测
  E0658,不可用;且默认 hook 会打印原始 payload,不能链接——见下条);
- panic.log 于 serve 启动时**预建**(0600 + regular-file 校验一次完成),hook 内只写已持句柄
  ——hook 内做 open/chmod 会引入二次故障面;
- 独立锁,不碰主写入器(hook 可能在主锁被持有时触发);
- **stderr 副本同规脱敏**:不调用默认 hook(它打印原始 payload——含密钥的 panic 消息会原样
  进 stderr,而 stderr 常被 nohup/journal 持久化),改为输出净化+脱敏后的摘要;
- 逐段(消息/位置/backtrace)脱敏净化后以结构性换行拼接:段内换行与控制字符一律转义为
  可见字面,panic 消息无法伪造 panic.log 的行结构(CWE-117);
- 5MiB 超限改名 `panic.log.old`(单份归档),合计预算 10MiB 计入清理总量。

## D8|隐私:白名单纪律 + 纵深防御

- 主通道靠**字段白名单**(只记路径/计数/耗时/错误码/来源名;错误描述禁止内嵌原始行内容),
  启动摘要只记白名单变量,未知 `USAGEBOOK_*` 只记"已设置"不记值——未来新增含密环境变量
  进不了日志;
- 纵深:全链路(console/文件/panic)控制字符转义净化;panic 通道加禁密标记词替换
  (词级 `[REDACTED]`,保守到 `task-` 这类 benign 词也会被吞——安全优先,panic 低频可接受);
  家目录统一缩略为 `~`(贴日志时的主要泄露面);
- 目录 0700、文件 0600;`USAGEBOOK_LOG_DIR=off` 整体关闭(但清理照常执行)。

## D9|输出契约(console 钉死 stderr)

`--json` 模式的 stdout 是脚本消费的管道——tracing-subscriber 的 fmt 层**默认写 stdout**,
因此 console 层必须显式 `with_writer(io::stderr)`;这是有契约测试钉死的(降级 fixture 下
`--json | jq` 必须不破)。同理,订阅器初始化必须在 `Args::parse()` 之后(clap 对
`--version`/`--help` 先退出,初始化抢跑会破坏 `--version` 全等输出)。人机消息(参数校验/
行动指引/进度)不进 tracing——保留裸 `eprintln!` 直出,否则套上时间戳前缀且在默认级别下
从用户眼前消失;双轨站点的 console 重复用 `-usagebook_cli` EnvFilter 指令抑制。

## D10|测试方法

单元:注入时钟(可变偏移)/注入写失败与 rename 失败/毒化锁恢复;集成:子进程拉起真实二进制
(规避全局 subscriber 与 hook 单例),契约 gate(`--json` 纯净/`--version` 全等/双实例降级)、
禁密(canary + 诱饵环境变量)、权限断言。曾以**变异验证**(人为破坏实现点确认测试变红)
校准测试网密度。
